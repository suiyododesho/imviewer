# site仕様書

## 目的

### webサイトのように画像を閲覧できるhtmlコンテンツのデザイン

ローカルで使う、2～3階層にかけて断片的に保存された画像コンテンツをリンクやナビゲーションを使って行き来できるようにし、一つのwebサイトのように閲覧できるようにすることを目的とする。

ローカルで完結させることを目的とするが、httpサーバを立てた場合はそのままwebサイトとしても機能するようにする。

### ハイパーリンクのメンテナンスツール

ローカルhtmlコンテンツのハイパーリンクをメンテナンスするためのツールを提供することも目的とする。具体的には、structure.jsonの内容をもとに、コンテンツの構成を表すツリー構造をjsファイルとして形成し、これをもとにナビゲーションhtmlを実現する機能を提供する。

## コンテンツのディレクトリ構成
コンテンツは、以下のようなディレクトリ構成を持つことを想定する。
単純に、画像が入ったディレクトリやPDF、cbzなどのファイルが`contents/`以下に階層化されて配置されるというだけである。

```
contents/

├── photobook/
│   ├── xxx/
│   │   ├──xyz/
│   │       ├── xyz_01.cbz
│   │       ├── xyz_01_cbz_tn/
│   │       │    ├── cover.jpg
│   │       ├── xyz_02.cbz
│   │       ├── xyz_02_cover.jpg
│   │       ├── xyz_02_cbz_tn/
│   │       │    ├── cover.jpg
│   │       ├── ...
│   │
│   ├──hij.cbz
│   ├──hij_cbz_tn/
│   │  ├──cover.jpg
│   ├──klm.cbz
│   ├──klm_cbz_tn/
│   │  ├──cover.jpg
│
├── comic/
│   ├── yyy/
│   │   ├── yyy_vol1/
│   │   │   ├── thumbnail/
│   │   │   ├── hoge.jpg
│   │   │   ├── huga.jpg
│   │   │   ├── ...
│   │   ├── yyy_vol2/
│   │   │   ├── thumbnail/
│   │   │   ├── hoge.jpg
│   │   │   ├── huga.jpg
│   │   │   ├── ...
│   │
│   ├── zzz/
│   │   ├── zzz_vol1.pdf
│   │   ├── zzz_vol1_pdf_tn/
│   │   │    ├── cover.jpg
│   │   ├── zzz_vol2.pdf
│   │   ├── zzz_vol2_pdf_tn/
│   │   │    ├── cover.jpg
│   │   ├── zzz_vol3.pdf
│   │   ├── zzz_vol3_pdf_tn/
│   │   │    ├── cover.jpg
│   ...
├── structure.json
├── index.html
├── (あとは必要に応じて作る)
```

- index.htmlは、トップページ。
- contents以下は、コンテンツを格納するディレクトリ。`photobook/`や`comic/`は、コンテンツのサブディレクトリ。`photobook/`や`comic/`の中には、さらにサブディレクトリを介して画像やPDFなどのファイルが格納されるケースが多い。(`photobook/`や`comic/`はあくまで例であり、実際のディレクトリ名は任意である)
  - 画像ディレクトリ配下の`thumbnail`は、サムネイル画像を格納するディレクトリ。サムネイル画像は、ナビゲーションhtmlで利用する。
  - pdfやcbzなどのファイルとサムネイル画像は、同一ディレクトリに配置する。例えば、`hij.cbz`と`hij_cbz_tn/`のようにする。
  - サムネイル画像フォルダには`cover.jpg`という名前で表紙用のサムネイル画像を配置することを想定する。例えば、`hij_cbz_tn/cover.jpg`のようにする。これがナビゲーションhtmlで企画バナーやギャラリーサムネイルとして利用されるイメージである。
  - サムネイル画像フォルダには連番でサムネイル画像を保存する。これはコンテンツの表示画面で利用されるイメージである。例えば、`hij_cbz_tn/001.jpg`、`hij_cbz_tn/002.jpg`のようにする。
- `structure.json`は、コンテンツの構成を記述するjsonファイル。
  - `structure.json`の内容は、コンテンツの構成を表すツリー構造になっている。
  - `structure.json`の内容をもとに、ナビゲーションhtmlを生成する。(実際は、jsonデータを静的データとして持つjsファイルに変換することでナビゲーションhtmlを実現するイメージ)
- コンテンツの種類として想定しているのは以下。
  - 画像が入ったディレクトリ(dir)
  - PDF(pdf)
  - cbz,zipなどの圧縮ファイル(archive)
  - htmlファイル(html)
  - その他、必要に応じて追加することもあるかもしれない。

**keyword**
- `structure.json`: コンテンツの構成を記述するjsonファイル。ナビゲーションの階層構成や名称表記をここで定義し、これをもとに1フォトギャラリー単位のコンテンツを結びつけたナビゲーションを動的に実現する。詳細仕様は後述。

## コンテンツの概念構成・ナビゲーション仕様

コンテンツの概念構成は、以下のようになっている。(xxxやyyyは、実際には具体的な人名が入る)
`[***]`が概念で、`:***`が実際のファイルorディレクトリを表している。
```
[トップページ]:index.html 
├── [ジャンル1]:comic/
|   ├── [シリーズ1]:comic/onepiece/
|   |   ├── [コンテンツ 01]:comic/onepiece/onepiece 01.pdf
|   |   ├── [コンテンツ 02]:comic/onepiece/onepiece 02.pdf
|   ├── [シリーズ2]:comic/baki/
|   |   ├── [コンテンツ 01]:comic/baki/グラップラー刃牙 01巻/
|   |   ├── [コンテンツ 02]:comic/baki/グラップラー刃牙 02巻/
|   ├── [シリーズなし]:(ディレクトリなし)
|   |   ├── [コンテンツ 01]:comic/yyy 01/
|   |   ├── [コンテンツ 02]:comic/yyy 02.pdf
|   |   ├── [コンテンツ 03]:comic/yyy 03.cbz
|   ...
├── [ジャンル2]:photo/
|   ├── [シリーズ1]:photo/friday/
|   |   ├── [コンテンツ 01]:photo/friday/xxx 01/
|   |   ├── [コンテンツ 02]:photo/friday/xxx 02/
|   ...
├── [ジャンル3]:gamecg/
|   ├── [シリーズ1]:gamecg/maker01/
|   |   ├── [コンテンツ 01]:gamecg/maker01/game01/scene01/
|   |   ├── [コンテンツ 02]:gamecg/maker01/game01/scene02/
|   ...
├──...
├── [全人物一覧(ジャンル1)]:index.html?genre=comic&person=...
├── [全人物一覧(ジャンル2)]:index.html?genre=photo&person=...
├── ...
```
ポイントは、

概念としては[トップページ] -> [ジャンル] -> [シリーズ] -> （[コンテンツ] ->） [フォトギャラリー]の階層構造が形成される。

概念の具体例を挙げる。

ナビゲーション階層に登場する概念は、以下のようなものである。

ジャンル：写真集、漫画、イラスト集など。
シリーズ：one piece、ジョジョの奇妙な冒険などの作品名、写真集ならfriday、bejeanなど。写真集はシリーズがないケースも多いので、シリーズなしのケースも想定する。
コンテンツ：シリーズに属する企画のコンテンツ。例えば、one pieceならone piece 1巻、2巻など。写真集なら、friday 2023年1月号、bejean 2023年2月号など。シリーズなしのケースでは、コンテンツがシリーズの役割も兼ねることになる。
コンテンツが2階層以上の階層構造を持つケースもある。例えば、ゲームCGのシーン集などは、シリーズ -> コンテンツ -> フォトギャラリーのような3階層構造になることがある。

ナビゲーション階層に登場する概念もある。

人名の概念は階層ナビゲーションに表示されるものとは別の概念であることに注意する。人物別一覧ページに使う。
人名：作者、モデルなど。写真集ならモデルが人名にあたる。漫画なら作者が人名にあたるのだが、漫画の場合は無しとする。写真集の場合、不特定多数のモデルが登場するケースも多いので、その場合は「なし」とする。（表向きは「なし」と表示するが、内部では複数の人名を定義できる。検索時に利用する）


### ナビゲーション仕様

企画、人名、フォトギャラリーの数を考慮し、ユーザーが「いまどこにいるか」「次にどこへ行けるか」を常に判断できる構成にする。

### structure.json

structure.jsonとjsを用いて、webサイトのナビゲーション・コンテンツを動的に形成させるようにする。

#### jsonの構成
structure.jsonは、以下のような構成を持つことを想定する。(jsonc形式でコメントも入れている)
```jsonc
{
  "contents-root": "contents",  // コンテンツのルートディレクトリを定義する。これを基準にして、各コンテンツのpathが解釈される。
  [
    "comic": {
      "name": "漫画"
      "00001": {  // コンテンツシリーズの定義。構成要素はphotoと同様。
          "name": "",       // コンテンツ名。画面表示の際は、これを優先して表示する。未設定の場合は、ディレクトリ名を表示する。
          "series": "",     // シリーズ名。漫画なら作品名、写真集ならテーマ名など、そのコンテンツの大分類を指定する。例えば"one piece1巻"に対するシリーズ名は"one piece"。シリーズがない場合は空文字列とする。空文字の場合は"未分類"として扱う。シリーズが複数ある場合は、代表的なものを指定する。
          
          "main-person": "",  // シリーズ配下の従属コンテンツ全体で共有する代表人物。原則コンテンツ単位では指定しない。
          "persons": [],  // main-person以外の人物リスト。シリーズ配下の従属コンテンツ全体で共有する。原則コンテンツ単位では指定しない。
          // "type": "",      // typeはpathから判別できるため、冗長なので不要。
          "labels": [],   // 分類用のラベル。
          "note": "",     // 企画に対する補足説明などがあれば記載する。特になければ空文字列とする。
          "contents": [   // シリーズ配下ディレクトリからメンテナンスツールで再生成するリスト。自動化対象：空欄可
            {
              "path": "",   // contents-rootからの相対パス。自動化対象：空欄可
              "cover": "",  // そのコンテンツのカバー画像パス。サムネイル作成時に生成されたカバー画像を設定する。自動化対象：空欄可
              "name": "",   // ディレクトリ名を設定する。自動化対象：空欄可
              "note": "",   // 手動追記欄。再生成時に空欄へ戻ることを許容する。自動化対象：空欄可
            }
            // ...
          ],
          "exturl": [     // 外部URLもしくは内部のhtmlのリスト。必要に応じて追加する。URLとキャプションを指定する。 ここに指定すると、シリーズ単位で外部URLもしくは内部htmlへのリンクをナビゲーションに表示することができる。
            {
              "url": "",
              "caption": ""
            }
            // ...
          ]
        }
    },
    "photo": {
      "name": "写真集"
      "00001": {
      // コンテンツシリーズの定義。構成要素はcomicと同様。
      }
    },
  ]
}
```

- `contents` の運用ルール
  - シリーズ配下ディレクトリからメンテナンスツールで再生成する。
  - 生成値は `name=ディレクトリ名`, `path=contents-rootからの相対パス`, `cover=生成済みカバー画像パス`, `note=空文字` を原則とする。
  - ディレクトリ名変更後は再生成を行い、`note` が空欄に戻ることは許容する。
  - `main-person` と `persons` はシリーズ配下の従属コンテンツ全体で共有する設計とし、コンテンツ単位項目は持たない。

#### 作業成果物の格納場所

- structure.jsonは、contents/ディレクトリに配置する。
- サイト全体設定ファイルは、siteディレクトリ直下に配置する。例えば、デフォルトシリーズを定義する`sitedesign.json`を置く。
- ナビゲーションhtmlは、contents/ディレクトリの直下に配置する。

#### site設定ファイル

- `sitedesign.json` のような別ファイルでサイト全体設定を管理する。
- 初期項目として `defaultSeries` を持たせる。
- `defaultSeries` は 01.企画一覧 を開いた時に最初に表示するシリーズ名を表す。
- `defaultSeries` が未設定または不正な場合は、structure.json に出現する最初のシリーズを使う。
- ローカルファイル運用を考慮し、ブラウザ実行時には JSON を直接 fetch せず、必要に応じて事前生成した JS を読み込んでもよい。

#### 1. ページ種別と役割、デザイン

デザインは本セクションで示した例のhtmlに近い形にして、かつ"2. 共通ナビゲーション部品"や"3. 画面遷移ルール"で示した仕様を満たすようにする。

サイトのテーマは白を基調とし、シンプルで見やすいデザインを目指す。既存のデザインを踏襲。

サムネイル画像は、structure.jsonで定義された画像を利用する。サムネイル画像がない場合は、代替テキストを表示する。

- 01.共通
  - 役割: 全ページ共通のナビゲーション部品を提供する。
  - 表示: ヘッダー、サイドメニュー、パンくずリスト、前後移動、現在地表示など。
    - ヘッダーにはサイト名と簡易検索を配置する。
    - サイドメニューにはシリーズ一覧を配置する。
    - パンくずリストは、トップ > ジャンル名 > シリーズ名 > ギャラリー名(コンテンツ名)の形式で表示する。
      - 前後移動は、同一コンテキスト内で前のページと次のページに移動するためのリンクを配置する。
      - 現在地表示は、選択中の企画・人物・ギャラリーを見た目を変えて強調表示する。
    - パンくずリストの右端には表示モード切替を配置する。カード式とリスト式の切り替えができるようにする。（02.シリーズ一覧・03.コンテンツ一覧のページのみ）
- 02.シリーズ一覧（トップ）
  - 役割: 全体の入口。シリーズを俯瞰し、人物またはシリーズ単位で次のページへ進む。
  - 表示: パンくずリストの下は2種類の表示モードを選択できる。
    - カード式(画面幅に応じた複数カラム表示)とし、左にサイドメニュー、右にシリーズ一覧を表示する。
    - リスト式(縦一列表示)とし、左にサイドメニュー、右にシリーズ一覧を表示する。
    - サイドメニューには「ジャンル一覧」という見出しを置き、structure.json のジャンルリストのオブジェクト名(`comic`や`photo`など)をユニーク化したリンク一覧を表示する。
    - シリーズリンクをクリックすると、そのシリーズに属する企画だけを右側に表示する。
    - シリーズ未設定の企画は「未分類」として扱う。
  - 表示: 以下のレイアウトを基本とする。画面幅に応じて、カード式は1～3列、リスト式は1列で表示する。
    - レイアウトイメージ(カード式)
    ```
    +-------------+---------------+ +-----------------------------+
    | [サムネイル] | シリーズ名     | | [サムネイル] | シリーズ名     |
    |             | 人名(main)    | |             | 人名(main)    |
    |             | コンテンツ数   | |             | コンテンツ数   |
    +-------------+---------------+ +-----------------------------+
    ...
    ```
    - レイアウトイメージ(リスト式)
    ```
    +-----------------------------------------------------+
    | [サムネイル] シリーズ名 / 人名(main) / コンテンツ数     |
    +-----------------------------------------------------+
    ...
    ```
  - レイアウト: 2列を基本とし、画面幅に応じて1列または3列に可変。
- 03.コンテンツ一覧のページ（02.シリーズ内のコンテンツ一覧）
  - 役割: 1シリーズのコンテンツ一覧を表示し、選択したコンテンツのギャラリーへ進む。
  - 表示: 02.シリーズ一覧と同様に、カード式とリスト式の切り替えができるようにする。
    - カード式は、シリーズ一覧のカード式と同様のレイアウトで、コンテンツのサムネイルと名称を表示する。
    - リスト式は、シリーズ一覧のリスト式と同様のレイアウトで、コンテンツのサムネイルと名称を表示する。
    - レイアウトイメージ(カード式)
    ```
    +-------------+---------------+ +-----------------------------+
    | [サムネイル] | シリーズ名     | | [サムネイル] | シリーズ名     |
    |             | 人名(main)    | |             | 人名(main)    |
    |             | ページ数      | |             | ページ数      |
    +-------------+---------------+ +-----------------------------+
    ...
    ```
    - レイアウトイメージ(リスト式)
    ```
    +-----------------------------------------------------+
    | [サムネイル] シリーズ名 / 人名(main) / ページ数     |
    +-----------------------------------------------------+
    ...
    ```
  - レイアウト: 2列を基本とし、画面幅に応じて1列または3列に可変。
- 04.コンテンツギャラリーページ
  - 役割: コンテンツの閲覧ページ。コンテンツの内容を表示する。
  - 表示: 既存の`gallery.html`を踏襲する。structure.jsonの内容をもとに、ギャラリーのタイトルや説明文を表示する。
  - レイアウト（既存の`gallery.html`をreverseして作成したもの）:
    - 画面全体は「ヘッダー」「パンくず」「閲覧領域」「下部ナビゲーション」の4段構成とする。
    - ヘッダーとパンくずは上部に固定的に配置し、主閲覧領域は残り高さを使って表示する。
    - 主閲覧領域はダーク背景のビューアとして構成し、左側にサムネイルストリップ、右側にメディア表示ステージを配置する（PC時）。
    - サムネイルストリップ:
      - PCでは縦スクロール、スマートフォン幅では横スクロールに切り替える。
      - 各サムネイルは選択状態を枠色で強調する。
      - 動画項目は専用見た目（動画ラベル/拡張子表示）を持つ。
    - メディア表示ステージ:
      - 画像/動画はcontainで全体表示し、表示枠内に収める。
      - 画像表示時はズームUI（スライダー＋倍率表示）を右上に重ねる。
      - ズームUIはPCで縦スライダー、モバイルで横スライダーに切り替える。
      - 拡大時はドラッグ移動を許可し、カーソル状態をgrab/grabbingで切り替える。
      - 「全サムネイル表示」トグルをステージ左下に配置し、押下時はステージ全面にサムネイルパネルを重ねて表示する。
      - サムネイルパネル構築中は、ステージ中央に処理中オーバーレイを表示する。
    - 下部ナビゲーション:
      - 「前へ」「次へ」「全画面」ボタン、外部リンク（元HTMLを別タブで開く）、ページ内ナビゲーション、現在位置情報を配置する。
      - 最下段にキーボード/マウス操作ヘルプを表示する。
    - レスポンシブ:
      - 768px以下では、主閲覧領域を縦積み（上:サムネイル、下:メディア）に変更する。
      - 480px以下では、下部ナビボタンを2列グリッド化し、全画面ボタンは全幅表示する。
      - 小画面ではズームUIを下部中央寄せに再配置し、タップ操作を阻害しないようにする。
    - 視認性/操作性:
      - 主要操作要素（サムネイル、トグル、ボタン）はfocus-visibleでフォーカス可視化する。
      - 閲覧領域はダーク、下部ナビはライト基調とし、閲覧没入感と操作の視認性を両立する。
- 05.全人物一覧ページ（実装済み拡張）
  - 役割: 全企画を横断して人物名の一覧を提示し、人物起点でコンテンツへ遷移する入口を提供する。
  - 表示:
    - 人物名を先頭文字単位でグルーピングして表示する。
    - 各人物はチップ型リンクとして表示し、クリックで `index.html?person=...` に遷移する。
    - サイドメニューにはシリーズ一覧と「全人物一覧」リンクを表示する。
  - レイアウト: 01～03と同様に、左サイドメニュー + 右メインカラム構成とする。

#### 2. 共通ナビゲーション部品

- サイドメニュー領域
  - 01, 02, 03, 05 のパンくずリスト直下に表示する。
  - 「ジャンル一覧」見出しと、series値をユニーク化したリンク一覧を表示する。
  - 「未分類」はシリーズ未設定企画の受け皿として表示する。
  - サイドメニュー末尾に「全人物一覧」へのリンクを表示する。
  - 現在ページに対応するシリーズ/人物一覧リンクは active 表示にする。
- ヘッダー領域
  - 左: サイト名（クリックで01.シリーズ一覧へ戻る）。
  - 右: 簡易検索入力（人物名検索）。
  - PCでは上部固定、狭幅画面（768px以下）では通常フロー配置に切り替える。
- パンくずリスト
  - 区切りは `›` を使用する。
  - 各ページで現在地までの階層を表示し、現在地以外はリンク遷移可能にする。
  - 01ではパンくず右端に表示モード切替（カード/シンプルリスト）を表示する。
- 検索（人物名）
  - 01では入力中にシリーズ横断検索結果を描画する。
  - 01で `Enter` 押下時は、入力人物名に対する結果表示を確定する。
  - 01で `Escape` 押下時は検索語をクリアし、通常一覧に戻す。
  - 03, 05 では `Enter` 押下時に `index.html?person=...` へ遷移する。
- 前後移動
  - 03には同一企画内の人物順で「前へ/次へ」を表示する。
  - 04には「前へ/次へ」「全画面」を表示する。
- 外部リンク表示
  - 人物に `exturl` が定義されている場合、03に外部リンク群を表示する。
  - 04では「元のHTMLを別タブで開く」リンクを表示する。
- フォーカス可視化
  - 主要なリンク/ボタン/サムネイルに `:focus-visible` を適用し、キーボード操作時の現在位置を視認可能にする。


#### 3. 画面遷移ルール

- 01.シリーズ一覧
  - シリーズリンククリック -> 同ページで対象シリーズへ絞り込み表示（`index.html?series=...`）
  - 表示モード切替クリック -> 同ページ内でカード/シンプルリストを切替
  - 企画バナーまたは企画名クリック -> 02.企画ページ
  - 人物テキストクリック -> 03.特定人物のフォトギャラリー一覧
  - 「全人物一覧」クリック -> 05.全人物一覧
  - `?person=` クエリ付き遷移時 -> 人物検索結果表示（シリーズ単位グループ）
- 02.シリーズのページ
  - 人物見出しまたは人物リンククリック -> 03.特定人物のフォトギャラリー一覧
  - ギャラリーサムネイルクリック -> 04.フォトギャラリーページ
- 03.特定人物のフォトギャラリー一覧
  - パンくずの企画リンククリック -> 02.企画ページ
  - ギャラリーサムネイルクリック -> 04.フォトギャラリーページ
  - 前へ/次へクリック -> 同一企画内の前後人物へ遷移
- 04.フォトギャラリーページ
  - サムネイルクリック -> 同一ギャラリー内の対象メディアへ切替
  - 前へ/次へクリック -> 同一コンテキスト内の前後メディアへ切替
  - 全画面ボタンクリックまたは `F` キー -> 全画面表示を切替
  - `Esc` キー -> 全サムネイル表示モードを解除
  - 「元のHTMLを別タブで開く」クリック -> 元コンテンツへ遷移
- 05.全人物一覧
  - 人物チップクリック -> `index.html?person=...` へ遷移し、01で検索結果表示
  - ヘッダー検索（Enter） -> `index.html?person=...` へ遷移

#### 4. 並び順と名称表示

- シリーズの並び順
  - 原則、structure.jsonの定義順を正とする。
  - 定義がない場合のみ、honey番号の昇順を代替として利用。
- 人物・ギャラリーの並び順
  - 原則、structure.jsonの定義順。
  - 同順位または欠損時は、ディレクトリ名の自然順ソート（数値を考慮した昇順）。
- 表示名
  - 画面表示名はstructure.jsonのlabelを優先。
  - ラベル未定義時はディレクトリ名をそのまま表示。

#### 5. 迷子防止・使いやすさ要件

- どのページにも「トップへ戻る」導線を配置する。
- 1クリックで到達できる候補数が多すぎる場合は、人物単位で折りたたみ表示を許可する。
- 01.企画一覧の人物はテキストリンクで表示し、画像に依存しない。
- 利用するサムネイルには必ずテキストラベルを併記し、画像が読み込めない場合でも内容を判別できるようにする。
- 検索結果や一覧が0件のときは、空表示にせず理由と戻り先リンクを表示する。

#### 6. リリース・バージョン管理仕様

システム更新とデータ更新は、別系統のバージョン管理として扱う。

##### 6-1. システムのバージョンアップ

- バージョンファイルは `site/version_sys.txt` を用いる。
- リリースタグ名は `release_ver_x.y` とする。
- 通常のシステム更新では、`y` を 1 増やす（例: `1.2` -> `1.3`）。
- メジャーバージョン更新では、`x` を 1 増やし、`y` は `0` に戻す（例: `1.3` -> `2.0`）。
- 実装コマンド例:
  - `python tools/release.py system`
  - `python tools/release.py system --major`
  - `python tools/release.py system --dry-run`
- システム更新パッケージは、`site/` 以下の内容を zip 化する。ただし以下は除外する。
  - `site/contents/`
  - `site/thumbnail/`
- system リリース時は Git tag を作成する。データは Git 管理外のため、system のみタグ対象とする。

##### 6-2. データのバージョンアップ

- データ版のバージョンファイルは `site/version_data.txt` を用いる。
- 旧名称 `site/version.txt` は `site/version_data.txt` に統一する。
- データ更新は従来どおり `site/history.txt` を基に差分管理する。
- `history.txt` は YAML 形式とし、未リリース差分は `next:` ブロックに保持する。
- 実装コマンド例:
  - `python tools/release.py data`
  - `python tools/release.py data --dry-run`
  - `python tools/release.py data --rollback`
  - `python tools/release.py data --rollback --version v1.2`
- データ更新パッケージには以下を含める。
  - `site/contents/photo/` 配下の差分ディレクトリ
  - `site/thumbnail/`
  - `site/structure.json`
  - `site/js/structure.js`
  - `site/js/gallery-pages.js`
  - `site/history.txt`
  - `site/version_data.txt`
- データ更新では Git tag は作成しない。

##### 6-3. 運用上の狙い

- **システム更新**: HTML / CSS / JS / ナビゲーションなどのロジックを更新する。
- **データ更新**: `site/contents/photo/` やサムネイルなどの追加データだけを更新する。
- これにより、システムとデータを別々に入れ替えられるようにし、更新作業時の影響範囲を分離する。

#### 7. データの追加・更新の手順

簡略して記載すると、コンテンツを追加して、シリーズの定義をjsonに書き、バッチファイルからメンテナンスツール「maint_build_structure.py」を実行する。

詳細は以下。

- 前提
  - `structure.json` はシリーズ定義（`name`, `series`, `main-person`, `persons`, `labels`, `note`）を手動管理する。
  - 各シリーズの `contents` は、シリーズ配下ディレクトリを走査してメンテナンスツールで再生成する（自動化対象：空欄可）。
  - `contents[*].note` は再生成時に空欄へ戻ることを許容する。

- ユースケースA: 新規データ追加（シリーズ/人物/ギャラリーを追加）
  1. `site/contents/` 配下に対象ディレクトリ・メディアを追加する。
  2. `site/structure.json` のシリーズ定義を追加/更新する（`main-person` と `persons` はシリーズ単位で管理）。
  3. メンテナンスツールで `contents` を再生成する。
  4. メンテナンスツールで `site/js/structure.js` と `site/js/gallery-pages.js` を再生成する。
  5. 必要に応じて `history.txt` の差分管理を更新し、データリリース手順へ進む。

- ユースケースB: ディレクトリ名変更（リネーム）
  1. `site/contents/` 配下の対象ディレクトリをリネームする。
  2. `site/structure.json` のシリーズ定義（キー/表示名）を必要に応じて更新する。
  3. メンテナンスツールで `contents` を再生成する（`note` が空欄へ戻ることは許容）。
  4. メンテナンスツールで `site/js/structure.js` と `site/js/gallery-pages.js` を再生成する。

- ユースケースC: 既存データの軽微更新（画像差し替え、追加ページ）
  1. 対象ギャラリー配下のメディアを更新する。
  2. メンテナンスツールを差分モードで実行し、対象ギャラリーのみ `gallery-pages.js` を更新する。
  3. サムネイル再生成結果と `history.txt` を確認する。

- ユースケースD: 全量再構築（定期メンテナンス/破損復旧）
  1. `contents` を全シリーズ対象で再生成する。
  2. `site/js/structure.js` と `site/js/gallery-pages.js` を全量再生成する。
  3. 生成物の整合性（リンク切れ、件数、表示確認）を検証する。

- 期待するツール分割（pythonファイル単位）
  - `tools/maint_build_structure.py`:
    - 入力: `site/structure.json`, `site/contents/`
    - 出力: 更新済み `site/structure.json`（`contents` のみ再生成）
  - `tools/maint_build_gallery_pages.py`:
    - 入力: `site/structure.json`, `site/contents/`
    - 出力: `site/js/gallery-pages.js`、必要なサムネイル
    - オプション: `--diff`（`history.txt` 利用）
  - `tools/maint_build_structure_js.py`:
    - 入力: `site/structure.json`
    - 出力: `site/js/structure.js`
  - `tools/maint_sync_history.py`:
    - 入力: `site/contents/photo/`, `site/history.txt`
    - 出力: 更新済み `site/history.txt`

- 当面の暫定運用（現行スクリプトが改修完了するまで）
  - 現行 `tools/build_gallery_pages_map.py` は `structure.js` / `gallery-pages.js` 生成と `history.txt` 追記を担う。
  - ただし本仕様では、最終的に「`contents` 再生成」と「JS生成」を分離した運用へ移行する。


#### 8. その他支援ツール

- `tools/build_site_config.py`
  - `site/sitedesign.json` などのサイト全体設定の生成/更新を支援する。
- `tools/generate_thumbnails.py`
  - 画像群からサムネイルを生成する。
- `tools/extract_thumbnails.py`
  - アーカイブ/PDF等からサムネイル抽出を行う。
- `tools/history_manager.py`
  - `site/history.txt`（YAML）の読み書き・差分管理ロジックを提供する。
- `tools/release.py`
  - system/data のリリース処理（バージョン更新、パッケージ作成、ロールバック）を行う。
- `tools/maintenance.bat`
  - 日常運用向けに複数メンテナンス処理をまとめて実行する。

- 補足
  - 本仕様に合わせ、データ更新系の処理は「`structure.json` の `contents` 再生成」「派生JS生成」「history同期」を独立実行できる構成へ段階的に移行する。


#### 9. アクセシビリティ・操作性

- キーボード操作
  - Tabで主要リンクに到達できること。
  - Enterで遷移できること。
- フォーカス可視化
  - 現在フォーカス中の要素を明確に視認できるスタイルを適用する。
- 代替テキスト
  - 企画バナー・ギャラリーサムネイルには意味のあるaltを設定する。
  - 01.企画一覧の人物テキストリンクは、リンク文言だけで遷移先が判別できるようにする。

#### 10. ローカルファイル運用の制約

- すべてのリンクは相対パスで記述する（file:// 絶対パス依存を避ける）。
- サーバー機能に依存する挙動（API通信、動的ルーティング、認証）は導入しない。
- URLクエリに依存せず、structure.jsonとディレクトリ構造だけでページを再現できるようにする。

#### 11. 受け入れ確認観点

- 01 -> 02 -> 03 -> 04 の往復がマウスのみで完結する。
- 同じ往復がキーボード主体でも完結する。
- 01.企画一覧で人物がテキストリンクとして表示される。
- structure.jsonに定義された順序・名称が画面に反映される。
- 画像未読込・リンク切れ時に、ユーザーが前の階層へ戻れる。

## シリーズ、人物、ギャラリーの追加（保守拡張作業）の手順イメージ

photoディレクトリに新しいシリーズを追加すると、jsonの内容を更新するだけで、ナビゲーションhtmlに自動的に反映されるイメージ。

1. 新しいシリーズのディレクトリをphotoディレクトリに追加する。
2. 新しいシリーズのディレクトリには、さらに人物ディレクトリを追加する。
3. 人物ディレクトリには、さらにフォトギャラリー単位のコンテンツを追加する。
4. structure.jsonの内容を更新して、ナビゲーションhtmlに反映させる。

(1～3はhoney-xディレクトリを追加するイメージ。honey-xディレクトリの中には、人物ディレクトリ、その中にフォトギャラリー単位のコンテンツが入っている。この構造をjsonに反映させれば、サイトが完成する。)
